<Slide title="A dynamic system message" hideTitle>

<Column slideOnly>

A rule in the graph does nothing until the model sees it. `pinnedRules` adds an input processor that runs at **every step**, not once per turn, and puts every `Rule` node into the context.

It is a dynamic system message. The processor reads the rules, clears the previous copy by tag, and adds a fresh one. The rule is never in the message history, so the window has nothing to drop.

This is the same idea as a dynamic system prompt in other frameworks, applied per step.

</Column>

<Column slideOnly>

```ts title="In workshop.config.ts"
// STAGE 3: inject every Rule node from the graph into the context at every step.
pinnedRules: true,
```

</Column>

</Slide>

<Slide title="The processor">

<Column slideOnly>

`processInputStep` runs before each model call in the loop. The tag, `pinned-rules`, is what lets the processor replace its own message instead of adding a duplicate every step.

It also records which rules it pinned in `runtime.systemMeta`. That is how the trace you built in module 3 can show that a `SystemMessage` pinned a particular `Rule`. Check it later with `npm run query -- systemContext`.

</Column>

  annotations={[

```ts title="In src/workshop/processors/pinnedRules.ts"
async processInputStep({ messageList }: ProcessInputStepArgs) {
  if (!config.pinnedRules) return;
  const rules = await listRules();  // (1)
  messageList.clearSystemMessages(TAG);  // (2)
  if (!rules.length) return;
  messageList.addSystem(renderRules(rules), TAG);  // (3)
}
```
</AnnotatedCode>

<Slide title="Pinned is not enforced">

<Column slideOnly>

The agent asked. Nothing made it ask.

The rule is in the context, and a model that reads it will usually comply. In module 6, you move the check out of the prompt and into code, so a forgetful or manipulated model still cannot delete.

For now, notice what you gained: the rule survives a window that cannot hold it.
