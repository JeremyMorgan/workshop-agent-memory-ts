## Why the instruction never existed

Back to Summer Yue's inbox. Her instruction was given at the start of the conversation.

On the small test inbox, the conversation never got long enough to matter. On the real inbox, as reported, the context filled up and the agent's framework compacted it to make room. The original instruction did not survive.

</Column>

test inbox   short conversation, instruction kept

## A bug that only appears at scale

As far as the agent could tell, the instruction never existed. It was not disobeying her.

Testing on a small inbox gave false confidence. A window limit is a bug that only appears at scale.

This workshop's agent uses a history window rather than compaction, and the effect is the same. You give the agent a small window on purpose and watch the same thing happen to a fake inbox.

</Column>

<Column slideOnly>

```text title="Same failure, different mechanism"
Compaction      summary drops the instruction
History window  oldest messages drop out
```

</Column>

## The script

The scenario runs five turns against the stage 1 preset.

Turn 1 states the rule. Turns 2 to 4 ask the agent to read emails from Dana, Priya, Sam, the newsletters and HR, which adds up to ten `read_email` calls. Turn 5 says the inbox is cluttered and asks the agent to clean it up.

With `historyWindow: 6`, the rule is still in the window at turn 4 and gone at turn 5.

## What the agent did

Turn 1 is acknowledged: the agent says it will ask before deleting.

Turns 2 to 4 are tool-heavy. The agent lists and reads emails, one `read_email` call at a time, and each call and result is a stored message too.

Turn 5 is where it goes wrong. The rule has scrolled out, and the agent deletes ten newsletters.

</Column>

## Why it forgot

The agent did not decide to break the rule. The rule was never in front of the model at turn 5.

Short-term memory is a window, and a window drops the oldest messages first, with no regard for which ones matter. A rule is a message like any other.

Behaviour varies by model: a different `MODEL` may refuse to delete anyway, so if the failure does not reproduce, lower `historyWindow` to 4 and run it again.

</Column>

<Column slideOnly>

```text title="At turn 5, the window holds"
user:      "Read the first three newsletters..."   (turn 4)
assistant: tool calls and answer                    (turn 4)
user:      "My inbox is full of newsletter clutter..."
```

<Slide title="Longer windows are not the fix" hideTitle>

<Column slideOnly>

## Longer windows are not the fix

A longer window delays the problem. It also fills the context with tool output the model does not need, which costs tokens and attention.

The rest of the workshop treats the window as one input among several. You will record what is in it, store what must survive it, and inject the rules the model must not lose.

</Column>

<Column slideOnly>

```text title="What each option costs"
Bigger window      more tokens, rule still leaves eventually
Summaries          lossy: the exact wording of the rule can change
Pinned rules       stored once, injected at every step
```

</Column>
